# Mobile Retry Matrix (v1)

Матрица описывает, когда Android-клиент должен повторять запросы автоматически.

| Случай | Пример | Retry | Действие клиента |
|---|---|---|---|
| Нет сети / timeout / I/O | socket timeout, unknown host | Да | Поставить в outbox, exponential backoff |
| HTTP 5xx | 500, 502, 503, 504 | Да | Retry с backoff, без потери `client_operation_id` |
| HTTP 401 unauthorized | истек access token | Условно | Обновить access через `/auth/refresh`, повторить 1 раз |
| HTTP 403 forbidden | нет прав | Нет | Показать ошибку, остановить автоповтор |
| HTTP 404 not_found | удаленная заявка | Нет | Обновить список/кеш, пометить операцию failed |
| HTTP 400 validation_error | пустой `mode`, невалидные данные | Нет | Исправление только пользователем |
| HTTP 409 invalid_state | заявка уже закрыта | Нет | Обновить карточку, снять локальный optimistic state |
| HTTP 409 conflict_fsm | нарушен порядок этапов или close rules | Нет | Показать причину, предложить “Обновить заявку” |
| HTTP 426 https_required | HTTP запрещен | Нет | Переключить base URL на HTTPS |

## Рекомендуемые интервалы backoff

Пример:

- 1 попытка: +2 сек
- 2 попытка: +5 сек
- 3 попытка: +15 сек
- 4 попытка: +30 сек
- далее: 60/120/300 сек (ограничить max)

## Важные правила

- Не менять `client_operation_id` между повторами одной операции.
- Выполнять операции в порядке создания (FIFO внутри типа очереди).
- Для `close` блокировать повторные локальные “close” до результата первой операции.
- После успешной синхронизации делать soft-refresh карточки заявки (`GET /requests/{id}`).
